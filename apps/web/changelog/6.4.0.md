title: Give your releases a home in your docs
---

RDX now has an optional changelog plugin. Write one release note per version in
Markdown or MDX, and RDX puts them on a **Changelog** page linked from the navbar.
The notes in `changelog/` have their own history, so you can publish release
notes even when you keep a single edition of your docs.

## Publish your first note

Run `rdx add changelog` to activate the plugin. Then run
`rdx changelog new 1.2.0` to create `changelog/1.2.0.md` with the version, date,
and a draft title. Write what changed and what readers should do next. RDX orders
the notes by date and renders the same Markdown components available in your docs.

Use `badge: breaking, deprecated` if the release needs both labels. The supported
labels are **Breaking changes**, **Security**, and **Deprecated**. Put a migration
guide or advisory in the optional `links` field to surface it below the release
title. See [Publish release notes](/docs/6.4.0/plugins#publish-release-notes) for
examples of both fields.

## Find, share, and follow releases

- **Versions** jumps to a release and highlights the note you are reading as you
  scroll.
- **Filter** appears when a note has a badge. Select one or more badges to narrow
  both the notes and the version list.
- The link icon beside the date copies a direct link to that release.
  **Copy this page** copies just that note's Markdown and frontmatter, and
  **View Markdown** opens the export in a new tab.
- The RSS icon opens `/changelog/rss.xml`. Add that address to a feed reader to
  follow new releases.

## Catch broken release links before deployment

`rdx check` and `rdx build` check links from release notes to documentation pages,
headings, and other releases, plus local images and downloads. A broken link in
the note body reports its line. A broken frontmatter link identifies the field,
such as `links[0].href`.
